# 3 分钟项目演示脚本

离线演示：全程不依赖任何 API Key 与网络。目标是在 3 分钟内讲清「这条诊断链路怎么分工、证据从哪来、它在哪里会错」。

## 零、开场前 1 分钟的准备（不计入 3 分钟）

1. 在项目根目录先起服务，**把后端切到进程内以压缩等待时间**（否则每跑一次要等约 8~12 秒，3 分钟讲不完）：

   ```powershell
   $env:MCP_MODE = "local"
   $env:USE_LLM = "never"
   & ".\.venv\Scripts\python.exe" -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```

2. 浏览器打开 <http://127.0.0.1:8000/>，确认页头状态条显示接口正常、本地直接调用、模板报告、BM25 和 5 组样例。此脚本显式禁用模型以保证离线演示；启用真实模型时应预留等待时间。
3. 提前把「正常（基线）样本」下拉切到 `normal_1797`，把「异常样本」下拉切到 `outer_race_1797`，确认采样率自动带出 `12000`、转速自动带出 `1797`（页面会按样例元数据自动填充，不用手敲）。
4. 心里记住下面这条**失败案例**一定要讲，它是全场最重要的部分。

> 如果现场需要验证 MCP 协议链路，再切换到 `stdio`：结论完全一样，只是每跑一次要等约 8~12 秒；公开演示默认使用 `local`。

## 一、时间轴脚本

### 0:00 - 0:25　讲问题与架构

**操作**：不点任何按钮，页面停在中栏「分析输入」区域；顺手指出左栏是卡片目录与会话窗口列表、右栏是对话对话框。

**说**：

> 这是工业设备故障诊断 Agent 工作台，页面是三栏工作台：左边是结果卡片目录和会话窗口列表，中间是输入与结果视图，右边是对话对话框。输入是同一测点、同一工况下的两段振动信号：一段正常基线、一段待诊断的异常信号。工业现场的痛点是：振动数据本身好采，但「谁来看、依据是什么、结论能不能追溯」很难保证。所以我把它拆成五层，各层只干一件事——**MCP 工具只算可复现的信号证据，RAG 只给故障候选和公开来源，Agent 只决定调用顺序和组织证据，大模型只负责把证据写成中文报告，FastAPI 只做接口**。
>
> 编排层用 LangGraph 固定图和条件分支控制步骤，模型不自主规划。页面上等下会实时看到的执行时间线，就是这张图每个节点、每次工具调用的真实事件流，不是前端动画。公开演示默认 BM25；实现了可选的向量混合检索路径，但真实召回尚未通过质量验收，保持关闭。
>
> 关键设计是：**故障类型必须来自知识库候选这个封闭集合，大模型永远不能成为故障类型的来源，也不能改写任何数值**。页面中的每个数字，都来自 `numpy/scipy` 的计算结果。架构图、LangGraph 节点图、事件流与会话设计在 `docs/architecture.md`。

### 0:25 - 1:30　现场跑「正常 vs 外圈」（看实时时间线）

**操作**（边点边说）：

1. 指一下中栏两个下拉：「正常（基线）样本」= `normal_1797`，「异常样本」= `outer_race_1797`，采样率 `12000`、转速 `1797` 已自动带出。
2. 点击「开始分析」，让评审者盯着左栏默认选中的 **「执行过程」卡片**（内容显示在中栏）里的 Agent 执行时间线；跑完后左栏会话窗口列表会新增一个会话窗口（一次诊断 = 一个窗口）。

**说**：

> 点下去的这一刻，时间线先把 6 个节点全部预渲染成「等待」，然后随服务端事件逐个变成「执行中 → 已完成」——输入校验、振动信号分析、故障知识检索、证据充分性判断、模型诊断、报告汇总。这一段走的是 SSE 事件流接口，每个节点和工具的开始、结束、降级、分支选择都是后端执行到该处时真实发出的。
>
> 展开带工具调用的节点行，能看到 4 次工具调用明细：`validate_vibration_data`、两次 `extract_vibration_features`、`compare_normal_abnormal`，每行带一句话摘要。注意 RAG 检索不算工具调用，这是有意的——检索不是信号分析，它不该和工具调用预算混在一起，工具调用有硬上限。
>
> 「证据充分性判断」节点下面有一条绿色分支说明：「证据充分 → 调用模型生成诊断」。如果换成正常对正常，这里会变成「证据不足 → 跳过模型诊断」，模型节点标「跳过」，报告直接写「无法确认」——**分支是图上的真实条件边，不是展示文案**。
>
> 看结果横幅与摘要：`status = ok`，置信等级 low，RMS 变化与耗时在摘要区直接可见。点开「关键证据」卡片：RMS 从 0.0732 涨到 0.6756，上升 823%；峭度从 2.87 涨到 7.62，冲击成分明显增强。再点「信号分析」卡片里的「包络谱特征频率能量」：BPFO 的能量高达 2.494e-1，而基线里根本检不出这个成分，是最突出的特征频率成分。「知识检索与来源」卡片里候选第一条就是 `outer_race_fault`，相似度 0.4412，**判据核对 6/6 命中**；下面那条 `ball_fault` 检索分 0.3974 并不低，但滚动体条目的判据在这个外圈样本上 1 命中 / 3 未命中，alignment_score 被压到 0.2186、直接沉到末位——**规则层先把与数据矛盾的候选剔出去，模型看到的是规则筛过的排序**。

### 1:30 - 1:55　讲证据链与来源引用

**操作**：点开「Agent 决策依据」卡片扫一遍，点「信号分析」卡片看三条曲线、在其中一条上横向拖拽框选放大一个固定区间（再双击图内复位）并试听两路原始波形，再点「知识检索与来源」卡片看候选与来源，最后点「完整报告」卡片。

**说**：

> 「Agent 决策依据」把 Agent 为什么下这个结论摊开了：左边是候选类型与相似度、关键数值变化、主要频率证据，右边是 RAG 命中数与来源、置信度只有 low 的原因、有没有触发降级或复核提示——**这些全部是真实字段的展示，不是事后写的说明文**。
>
> 这里要专门讲一下**为什么必须有包络解调**。轴承的特征频率都很低：转频 29.95Hz、BPFO 107Hz、BPFI 162Hz。但局部缺陷的冲击能量被激励到的是 2~5kHz 的高频共振带，**直接在原始幅值谱上取这些低频点的能量，异常样本反而不比正常高**，没有区分度。所以工具先做共振带带通滤波、再 Hilbert 包络、再对包络做谱，能量才分得开。这是这条链路能work的前提。
>
> 再看「知识检索与来源」卡片里的知识来源：候选不是凭空来的，每条都挂着来源名称、URL 和 locator 定位。诊断报告里也刻意把三类信息分开写——**数据事实**（来自工具）、**知识依据**（来自知识库条目）、**推断结论**（Agent 组织）——就是为了让评审者能一眼看出哪句话是算出来的、哪句话是推理出来的。
>
> 报告第 9 节写了置信等级 low，原因是只检索到 1 条候选、缺少交叉印证。**系统不会在证据单薄时假装很有把握。**
>
> 报告第 5 节除了候选和相似度，还有一张**判据条款核对表**：每条候选下面逐条列出知识库写的判据，标出命中 / 未命中 / 未核对，并给出期望值与实测值。这张表由确定性引擎 `app/rag/criteria.py` 算出来，不经过模型——知识库现在 7 个条目共 **24 条具名判据条款**，每条带 `metric` / `op` / `value`，只允许用受控词表里的 **15 个指标 × 6 个比较符**，所以同一条款不可能两次核对出不同结果，也没有表达式注入。候选最终按「检索分 × 判据因子」重排成 `alignment_score`，但**阈值过滤仍按检索分**，候选集合和改造前完全一致，变的只是顺序。如果首位候选的判据与数据**冲突**（未命中数 ≥ 命中数），编排层会写一条 `warning`、把置信度强制压到 low、追加人工复核建议，模型也只能引用这个核对结果、不能改写——**规则能判的规则判、规则冲突交受限模型裁量、仍不决交人工确认**，这就是这一层的主线。
>
> 「信号分析」卡片里可以直接看波形：原始信号时域波形（正常那条平缓、外圈那条能看到周期性冲击的上下包络）、幅度谱、包络谱三条曲线叠着对比，红色是异常、蓝色是正常。曲线都是服务端算完降采样后传过来的——波形按 600 个分桶取 min/max 保住冲击尖峰，幅度谱和包络谱按「每桶取最大幅值」抽点以保住特征频率的窄峰，包络谱只画到 1000Hz，因为再往上没有特征频率。三条曲线都能在图上**横向拖拽框选放大**看固定区间（放大时横轴刻度跟着收窄、纵轴按区间重算），双击图内或点图右上角「重置视图」回到整段——缩放只重绘已经传过来的抽点序列，不会再向后端要数据，也不改变任何判据。下面两个播放器可以听原始波形：这是按峰值归一化后的去均值信号，只用来辅助感受冲击和调制形态，**不参与打分、也不是判据**。音频是按需加载的旁挂文件，不占诊断响应体积。

### 1:55 - 2:15　受控追问与右栏自由对话演示

**操作**：点开「诊断追问（受控）」卡片，在下拉里选「为什么判断为这个故障类型？」，点提问；再切到右栏对话框，输入一个自由问题（例如「候选故障有哪些，为什么怀疑它？」）；回答出现后**按 F5 刷新页面**，让评审者看到历史会话与对话被恢复，并可接着再问一句。

**说**：

> 诊断完成后可以就这次结果追问。卡片里的受控追问只能从 7 个固定问题里选，回答不是让模型自由发挥——后端从本次会话保存的候选、对比证据、频谱事实里**确定性拼装**，回答下方列出这次引用了哪些事实字段（`facts_used`），比如 `candidates[0]`、`comparison.evidence`，可核对、可追溯。
>
> 右栏是对话对话框，可以自由提问。配置了模型时由模型生成回答，但回答仍被同一份会话事实约束：出现候选之外的故障类型、或会话来源之外的链接，整段回答会因校验不过而作废、降级为后端确定性回答；没配模型也能用，只是回答标记不同。
>
> 刚才我刷新了页面：左栏会话窗口、时间线轨迹和右栏对话记录都原样回来了。会话与对话消息落盘在 SQLite（`data/sessions.db`），刷新甚至重启服务都不丢，可以在同一个会话里接着问。自由问答会把最近几轮对话带进提示词，用来理解「它」「这个故障」这类指代，但**事实依据始终只有本次会话**，历史对话不是新的事实来源。
>
> 如果拿错误会话问「为什么判断为这个故障」，系统会直接回答「当前诊断记录无法支持该结论。」；问清单外的问题会被 400 拦下并返回允许的问题清单。**追问、对话和诊断主流程一样：无依据不下结论。**

### 2:15 - 2:45　主动展示失败案例与修正（重点）

**操作**：把「异常样本」下拉改为 `ball_1797`（真实标签是滚动体故障），采样率与转速保持 `12000` / `1797`，再次点击「开始分析」。

**说**：

> 现在我把异常样本换成滚动体故障，**这个样本历史上被答错过，我就是要让你看到它现在怎么处理、以及它被修正到什么程度**。
>
> 看输出：横幅已经是正常结论，`status = ok`，候选第一条就是 `ball_fault`，相似度 **0.6283**；**修正前**这里输出的是 `inner_race_fault`、相似度 0.4614，和内圈样本的得分一模一样——那是个错答案。
>
> 为什么这次答案对了？点开「知识检索与来源」卡片：滚动体条目补了一条判据「**包络能量分散：各特征频率族能量相当、无单一主导族，主次难以区分**」，并且条目声明了自己的特征频率族 `frequency_family: BSF`（内圈 / 外圈 / 保持架分别声明 `BPFI` / `BPFO` / `FTF`）。检索排序因此把 `ball_fault` 顶到首位。
>
> 但证据本身**仍然是并列的**：点开「关键证据」卡片，包络谱 BPFI 族能量 4.20470e-4，BSF 族 3.92749e-4，**前者只高 7.06%**，低于 15% 的量级余量阈值，所以 `dominant_characteristic` 给出 `ambiguous=true` 和并列候选 `tied_candidates=[BPFI@162.186Hz, BSF@70.5838Hz]`。编排层的规则是：**只有当检索首位候选声明的特征频率族落在并列族内，才采信该候选继续出结论**——这里首位是 `ball_fault`、声明 `BSF`，正好落在并列族 [BPFI, BSF] 内，于是采信它、并强制把置信度下调为 **low**，报告里写明并列依据和一条现场复核建议；族不匹配或条目没声明族时仍按证据不足处理。
>
> 修正一共是「上一轮四项算法 / 查询修正 + 本轮知识库判据表达与并列族采信」：加量级余量判据（最高/次高低于 15% 不选优，改出并列候选）、对齐 BSF 口径（对外同时给出 1×BSF 与 2×BSF）、检索查询按特征频率族聚合（并列时两族一并写入）、扩大谱峰保留范围（从「全谱前 5 + 1kHz 以下前 5」到「全谱前 5 + 特征带内前 20」）；本轮再补知识库判据与 `frequency_family` 元数据、编排层按「首位候选的族落在并列族内即采信」给出结论、报告层把置信度下调为 low。
>
> 还是要如实说清**局限**：并列**没有被消除**（BPFI 与 BSF 仍只差 7.06%），本轮解决的是「检索首位不再落到内圈条目」，结论来自「条目声明的族与并列族一致」这一采信规则，**不代表主导族已经确定**，所以置信度只有 low、必须人工复核并列族；采信依赖条目 `frequency_family` 元数据；谱峰对齐证据客观上仍偏向内圈（原始频谱峰只与 BPFI 1/2/3 阶对齐，2×BSF = 141.17Hz 最近峰 148Hz、偏差 4.84% 超出 2% 容差）；弱冲击信噪比低与固定比例选带这两个根因未动；ball 场景过阈值候选只有 1 条。完整数字与效果实测见 `docs/evaluation.md` 第五节。

**为什么演示时要主动讲这个**：这个失败案例不是藏起来的 bug，而是被测试**显式断言**的确定行为（`test_normal_vs_ball_fault_tie_broken_by_top_candidate`：断言 `status=ok`、top1 `ball_fault`、`frequency_family=BSF`、置信 low 与 `trace.tied_resolution`，不加特判、不放宽断言）。能定位到「7% 能量差 + 缺量级余量判据 + BSF 口径不一致 + 知识库判据表达与族元数据缺失」这几层，并且**在把候选修对之后仍然如实承认并列未消除、置信度只有 low**，比一个漂亮的分数更能说明工程判断力。**5 个样例也从来不支撑任何准确率结论。**

### 2:45 - 3:00　讲局限与收尾

**操作**：不动鼠标，或者切到 `docs/evaluation.md` 第七节「已知局限与未验证项」。

**说**：

> 最后如实交代边界。第一，公开演示默认关闭混合检索，真实 embedding 语义召回质量尚未评估；向量路径由离线假 embedding 测试覆盖。第二，真实模型成功路径已用 `scripts/smoke_llm.py` 跑通一次，但长期延迟、失败率和成本尚未统计。第三，Docker 镜像尚未实际构建运行，本机只做了 Dockerfile 静态检查。第四，只覆盖 12k 驱动端、0 hp、1797rpm 一种工况，每个样本只有 1 秒。
>
> 所以这个原型的价值不在准确率，而在于**把「信号算法可信、证据可追溯、结论有边界、失败可复现」这条架构讲清楚了**。它离生产诊断系统还差自适应选带、多测点多工况验证和严重程度分级，这些是下一步。

## 二、断网 / 无 Key 预案

演示本身**完全不需要联网，也不需要任何 API Key**：

- 5 个内置样例都是仓库里的本地 CSV（`data/samples/*.csv`），不下载、不请求外部接口。
- 未配置模型 Key 时，`settings.llm_available=false`，系统**直接走模板化报告**，字段结构与接模型时逐字段一致，页面照常渲染，`/health` 会如实显示 `llm_available=false`。
- 未配置 embedding Key 时，检索**自动降级为 BM25**，`/health` 显示 `retrieval_mode=bm25`。本文演示的所有分数本来就是 BM25 分数。
- **向量库（Chroma）没配置也能启动**：检索直接走 BM25；即使配了 embedding 但 `data/chroma/` 索引不存在或不可用，也会自动降级为 BM25 并把原因写进 `trace.warnings`，**不会中断诊断**。

因此即使现场网络中断，「0:25 跑正常 vs 外圈」「2:15 展示并列族采信」两段都可以照常执行。如果现场需要真实 `stdio` 链路，也只用到本机子进程，不涉及外网。

**关于 `MCP_SERVER_CMD`**：适配层现在支持**含空格的路径**（用引号包住可执行文件，或写成 JSON 数组），项目根目录本身含空格也能正常走 `stdio`。解析或启动失败会返回结构化错误 `invalid_server_command`，不抛裸异常；演示若不想等子进程启动，把 `MCP_MODE` 设成 `local` 即可。

## 三、现场提问的兜底答法

| 可能被问到 | 一句话答法 |

| 准确率多少？ | 5 个样例不支撑任何准确率结论，我不给这个数字；我能给的是 7 个端到端场景的真实 status 与候选，以及 1 个已定位根因、已修正为正确候选但保留并列局限的失败案例。 |
| 滚动体样本现在答对了吗？ | 答对了候选，但置信度只有 low、并列没被消除。top1 已是 `ball_fault`（0.6283，`frequency_family=BSF`），但 BPFI/BSF 包络能量仍只差 7.06%，结论按「首位候选的族落在并列族内即采信」给出并把置信度下调为 low，**不代表主导族已确定**，仍需人工复核并列族。 |
| 为什么不用大模型直接看波形？ | 模型不能保证可复现，也改不了数值；故障频率对不对、能量涨了多少必须由算法算。模型只负责表达。 |
| 为什么 MCP 和 RAG 要分开？ | 一个是「算」，一个是「查」：MCP 的契约是数据进、证据出，RAG 的契约是证据进、候选+来源出。混在一起就无法分别替换和分别测试。 |
| 候选表里的「判据核对」是什么？为什么不让模型判断？ | 知识库 7 个条目共 24 条具名判据，用受控词表（15 指标 × 6 比较符）由确定性引擎逐条核对本次数据，给命中 / 未命中 / 未核对三态，并按「检索分 × 判据因子」重排；模型只能引用、不能改写。例：外圈样本上滚动体条目 1 命中 / 3 未命中，alignment 由 0.3974 压到 0.2186 沉末位。 |
| 没有候选怎么办？ | 直接置 `insufficient_evidence`、报告写「无法确认」、跳过模型，绝不硬凑故障类型。 |
| 正常样本当异常样本会怎样？ | 被 `_no_significant_change` 拦下，同样输出 `insufficient_evidence`，且 `candidates`、`sources` 一并清空、不留残留。 |
| 为什么用 LangGraph 图，不让模型自己决定调哪个工具？ | 诊断流程是固定且可审计的（校验 → 工具 → 检索 → 判断），用图表达节点顺序和条件分支，模型只负责在候选集合内选一个并组织语言，不能改变流程。 |
| 页面时间线是真实执行还是前端动画？ | 真实的：诊断走 SSE 事件流，节点/工具的开始结束、重试、降级、分支都是后端执行到该处时发出的，前端零模拟；SSE 意外中断才降级同步接口，并用 `trace.nodes` 如实重建时间线（没执行的节点显示「等待」）。 |
| 受控追问会调用大模型吗？ | 不会。7 个固定问题，回答由后端从会话保存的事实确定性拼装，`facts_used` 列出引用的字段；无依据就答「当前诊断记录无法支持该结论。」 |
| 右栏自由问答呢？ | 配了模型时由模型生成，但回答被两道校验约束：出现候选外故障类型或会话外链接就整段作废、降级为确定性回答；无依据时答「当前诊断记录无法支持该结论。」，不硬答。 |
| 刷新页面或重启服务后会话还在吗？ | 在。会话与对话消息落盘在 SQLite（`data/sessions.db`），刷新后左栏会话列表、时间线轨迹、右栏对话都按会话恢复，可接着追问；超过 50 个会话按创建时间淘汰最旧的。多轮只带最近 3 轮进提示词，事实依据仍只有本次会话。 |
| 混合检索为什么是 0.6 / 0.4？ | 向量分管语义、BM25 分管术语精确匹配（查询里全是 BPFI、2×BSF 这类专有词），两分各自归一化到 [0,1] 后加权融合；索引不可用时整条降级为纯 BM25。 |
